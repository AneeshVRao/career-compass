7. ~~**Sign-in silently did nothing before the page hydrated.**~~ **Fixed.** Five specs failed identically, stuck at `http://localhost:8080/login?`, with no error rendered. It looked exactly like a cookie/session bug — the guard bouncing a freshly signed-in user — and it was not: `signInWithPassword()` was never called at all. There was **no request to Supabase's `auth/v1` endpoint and no cookie ever set**. `/login` is SSR'd, so the form is on screen and clickable before React attaches `onSubmit`; a click in that window performs a **native** form submit, which reloads `/login?` — the empty query string being the tell, since no input carries a `name` (which is also why no credential ever reached the URL). Typing was lost the same way: it landed only in the DOM, and hydration then reset the controlled inputs to their empty `value` prop. A human never hit this because typing an email and password takes longer than hydration; Playwright fills and clicks in milliseconds. Fixed with one native attribute — a `<fieldset disabled>` around the form gates the inputs and submit button together, and a disabled default button also suppresses implicit Enter-key submission. The two controls outside the form (Google, and the sign-in/create-account toggle) got the same guard, since a pre-hydration click on those was silently a no-op — that is what stalled the signup spec on an unchanged heading. Playwright's actionability checks wait for enabled/editable, so the specs now block on hydration by themselves and needed no changes.
8. **`/auth/callback` has never once been executed.** Google OAuth is still off (item 2), so the entire OAuth branch is unexercised — and it is the one remaining place a cookie round-trip could fail the same way item 7 appeared to. `handleCallback()` calls `exchangeCodeForSession(code)`, which writes the session through `getSupabaseServerClient()`'s `setAll` → TanStack Start's `setCookie()`, and then returns a **hand-built** `new Response(null, { status: 302 })`. That only works if the framework merges the cookies recorded on the request context into a response the handler constructed itself. If it doesn't, OAuth sign-in sets no cookie and bounces straight back to `/login` — indistinguishable from the bug in item 7. Verify this the moment item 2 is done, and check for a real `Set-Cookie` on the 302 rather than trusting the redirect.
9. **Every navigation costs a round-trip to Supabase's auth server.** The root `beforeLoad` calls `fetchAuthUser()`, which calls `supabase.auth.getUser()` — a network call to `/auth/v1/user` that blocks the route resolving. Three fired for a single sign-in. `getClaims()` verifies the JWT locally against cached JWKS and would remove most of that latency, but it is a real change to how auth is validated (local signature check vs. asking the server), so it is a decision, not a cleanup. Related: if `getUser()` ever refreshes an expired token during SSR, the refreshed cookie is written via `setCookie()` after headers may already be flushed, and that write is silently lost — the same fragile class as item 8.

## Audit follow-ups, deliberately deferred

Two findings from the 4-way audit of `feat/multi-user-auth` were considered and consciously **not** implemented. Recorded here so they read as decisions rather than oversights — reopen them if the premises below stop holding.

- **Rate limiting on `/login`** — not needed, and not actually implementable here. `/login` is a client-side page: it calls `supabase.auth.signInWithPassword()` / `signUp()` straight from the browser to Supabase's hosted Auth API. This app owns **no** endpoint in the credential path (`src/lib/auth-server.ts` only _reads_ the session cookie), so any limiter added to this codebase would sit in front of a page an attacker can simply skip — they would post directly to `{SUPABASE_URL}/auth/v1/token` with the anon key, which is public by design. Supabase's own server-side per-IP limits on the token/signup endpoints are therefore the only enforcement point that exists, and they are sufficient. If the threat model tightens, the fix is to **lower the limits in the Supabase dashboard** (Auth → Rate Limits) — not to add a rate-limiting dependency to this repo. Revisit only if a custom server-side sign-in route is ever introduced.
- **Structured logging (Pino/Winston/Sentry) instead of `console.error`** — flagged by two audits; deferred as disproportionate. This is a small tool that went from one user to a handful, running as a single Render web service where `console.error` already lands in the platform's log stream and is greppable there. A logging framework would add a dependency and a config surface to buy structure nobody is currently querying. `console.error` stays. Revisit when there is somewhere that actually consumes structured logs (log aggregation, alerting, or error grouping) — that need, not the log calls themselves, is the trigger.
